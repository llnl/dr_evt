# Testing Guide

## Validation model

DR_EVT uses four complementary forms of validation:

- scheduler fixtures compare C++ output with expected schedules generated by
  separately written Python implementations;
- differential tests compare supported queue and API paths on the same
  workload;
- focused unit and integration tests exercise parsing, replay, buffering,
  configuration, streaming, power traces, and gRPC behavior; and
- [native scheduling comparisons](user-guide/SCHEDULER_VALIDATION.md) drive Flux
  through Fiction and Slurm through a virtual-time adapter under explicit
  policy and resource assumptions. The 2,000-job FCFS and license-enabled Slurm
  comparisons matched their recorded runs; reduced workloads isolate backfill
  differences. The Slurm adapter controls simultaneous event batching and
  verifies dispatch acknowledgements but leaves main-versus-backfill order
  uncontrolled, so these matches do not establish general scheduler equivalence.

The native OpenPBS scheduler-library comparison uses private vnodes and shared
server capacity. The `fcfs_1s_evt_group` policy matches every start and
completion in the original converted 2,000-job Lassen input. Default `fcfs`
has 1,433 differing schedules because it checks capacity between predicted
releases that OpenPBS groups together. Both policies are shown separately in
[OpenPBS validation](user-guide/OPENPBS_VALIDATION.md).
The [harness README](https://github.com/LLNL/dr_evt/blob/main/validation/openpbs/README.md)
gives setup and commands.

The separate `fcfs_1s_evt_group` policy reproduces that native forecast grouping.
Its native regression also checks pending-status and queue-drain queries
against ordinary FCFS: the grouped forecast can predict 11 while the real
job starts at a fitting release at 10. The placement-pass integration checks
the policy name through both CLI arguments and a Protobuf configuration.
Its focused C++ test covers inclusive groups, separated/lone releases without
an artificial delay, current fits, full-interval protection, retained calendar
events, actual streaming starts, and checkpoint continuation when enabled.
Direct-admission regressions check that a later fit does not justify starting
now, an end-boundary shortage is excluded from a half-open interval, and an
interior shortage blocks it. Point queries and grouped current-time checks
are covered too.
Placement-pass integration tests also exercise the command-line selector.
Quick CI runs its native test binary; full CI runs it and the integration
runner through CTest. The native OpenPBS comparison remains a separate replay.

Agreement between implementations is a regression and consistency check. It is
not independent proof that an algorithm is correct. Small scheduling fixtures
are therefore also designed for direct inspection against the policy rules in
[Backfilling Algorithms](BACKFILLING_ALGORITHMS.md).

Periodic backfill tests check that job starts expose a new bounded queue prefix
at the next tick while preserving the current tick's Q budget. A four-job
regression checks both immediate admission and future-reservation placement
when a candidate ends exactly at another reservation's start. Slurm-style
periodic hybrid/conservative backfill checks capacity at that endpoint;
Spur-style fixed periodic dispatch with arrival notifications excludes it.
The append-job tests distinguish protected periodic backfill from the
no-reservation diagnostic: a later fitting job may delay the head only in
the diagnostic mode, and simultaneous releases are processed before dispatch.
Checkpoint tests verify diagnostic continuation and reject a restore into the
protected policy; Python API tests cover the selector.
The append-job tests also check fractional endpoints, zero-duration capacity
queries, and unchanged reservation durations. See the
[endpoint rule explanation](user-guide/SCHEDULER_LOOPS.md#shared-terms).

The callback-driven ``FCFSEasyCustomScheduler`` has focused selector and API checks
plus golden-output comparisons for a targeted simultaneous-backfill case and a
2,000-job workload. The large comparison verifies that its job start and end
times match the default circular-buffer FCFS scheduler when the callback
selects candidates in FCFS order.

The append-job API test also covers Custom-FCFS time-accounted resource area,
capacity-aware instantaneous and aggregate utilization, and
prediction-horizon estimation. Its accounting cases include two allocations
and two releases at one timestamp and a scheduled-capacity reduction below
live occupancy. Its horizon scenario uses four running and four waiting jobs
to exercise successive running-job completion boundaries, the post-replay
full-capacity tail, the ``U=0`` fallback, future-arrival exclusion, and invalid
utilization values. The warm-start suite separately checks integrated
effective capacity across capacity changes at and after the start boundary.

The replay-based warm-start test exercises completed history, live historical jobs,
inherited waiters, boundary and future arrivals, empty tails, fractional and
simultaneous timestamps, every supported priority/backfill/queue combination,
and randomized differential workloads. Runtime-policy cases verify that
``actual``, ``limit``, and ``distribution`` affect only ordinarily scheduled
jobs while warmup jobs retain their recorded end times. Capacity coverage
includes overcommit after a reduction and a capacity change exactly at the
final warmup departure. A separate case protects the documented
``sim_start_time == 0`` behavior: zero disables replay-based warm start and
preserves a traditional full replay. Inclusive ``max_time`` boundaries are checked in
ordinary simulation, replay, and warm-start execution. Warm-start
self-consistency cases replay a simulation's own output at a
mid-run boundary and verify FCFS/EASY, conservative, hybrid, and SJF decisions
without a checkpoint; inherited waiters retain their original submit times.
CLI coverage accepts an ISO simulation start time,
rejects mixed timestamp encodings within one input file, and
rejects negative or non-finite values, simulation-format input, and progressive
file lists.

The queue-input parser test verifies both queue schemas and runtime validity:
a supplied replay runtime must agree with ``end_time - begin_time`` within the
timestamp tolerance, while a supplied simulation runtime must be finite and
no greater than ``time_limit``.

## Test inventory and commands

The Test Suite README is the source of truth for the maintained
[test inventory](https://github.com/LLNL/dr_evt/blob/main/tests/README.md#inventory)
and [runner commands](https://github.com/LLNL/dr_evt/blob/main/tests/README.md#build-and-run).

CTest discovers tests enabled by the current build configuration. Optional
features such as Protobuf, gRPC, MPI, Python bindings, and Catch2 add their
corresponding tests only when available.

Run the endpoint and periodic scheduling regressions with:

```bash
ctest --test-dir build --output-on-failure \
  -R '^(test_append_job_api|test_fixed_periodic_dispatch|test_periodic_backfill_reference|test_python_periodic_reference)$'
```

Quick CI runs the append API and both dispatch runners. Full CI runs all
configured CTest registrations with GCC and Clang, including queue-depth,
checkpoint/restart, and batch/streaming checks. Quick and full CI also run the
five OpenPBS harness audit tests, which need only Python's standard library:

```bash
python3 -m unittest discover -s validation/openpbs -p test_compare.py -v
```

These tests check the comparison harness, not native scheduling. Native Flux,
Slurm, and OpenPBS replays are reproduced separately with the validation
harnesses; OpenPBS requires its pinned source checkout and the Lassen trace.

Run only the replay-based warm-start behavior and CLI validation registrations with:

```bash
ctest --test-dir build --output-on-failure \
  -R '^(test_warm_start|test_warm_start_validation)$'
```

## Expected outputs

Scheduler fixtures normally contain:

- an input CSV;
- an `.expected_output.csv` scheduled-job trace; and
- when resource accounting is checked, an
  `.expected_resources.csv` resource trace.

Expected outputs should be regenerated only for an intentional behavior change,
then reviewed before they are committed. See the Test Suite README for
[fixture locations](https://github.com/LLNL/dr_evt/blob/main/tests/README.md#fixture-locations)
and [instructions for adding tests](https://github.com/LLNL/dr_evt/blob/main/tests/README.md#adding-tests).

## Distributed tests

gRPC tests start local servers and exercise the network protocol. The optional
MPI composite-stream test uses four ranks: two server ranks and two paired
client ranks. It validates synchronized equal-time and strictly ordered
composite arrivals. The exact launcher commands and fixture names are listed
under
[Distributed client/server tests](https://github.com/LLNL/dr_evt/blob/main/tests/README.md#distributed-clientserver-tests).

The Python single-coordinator integration test covers the deployment described
in [Client/Server Use Cases](user-guide/client-server-use-cases.md) and compares
each server's output with an independent batch simulation.

## Adding tests

Place a new test with the runner for the behavior it covers, keep generated
artifacts outside the repository root, and document the new case in the test
suite inventory. Tests that add a user-visible option or format must also
update the corresponding user-guide reference page.
