# DR_EVT Test Suite

Comprehensive test suite for the DR_EVT HPC Job Scheduler Simulator.

## Overview

DR_EVT has tests organized by purpose:
- **Comprehensive (34)** - Verify scheduler algorithm correctness with dual validation
- **Unit (7)** - Basic I/O and format tests (2 currently broken - see below)
- **Feature (3)** - Policy and mode comparisons
- **Scale (7, 4 working)** - Larger job counts than comprehensive/'s ceiling (3 currently broken - see below)
- **Replay (3, verified against more)** - Verify replay reproduces simulation

Note: "Correctness" below refers to matching the Python reference
implementation's output, not independent mathematical verification - see
`docs/TESTING_GUIDE.md` for what that distinction means in practice.

## Quick Start

```bash
# Build first
cd build && cmake .. && make -j4

# Run all correctness tests (most important)
./tests/test_all_dr_evt.sh

# Run unit tests
./tests/run_unit_tests.sh

# Run feature tests
./tests/run_feature_tests.sh

# Run replay tests
./tests/run_replay_tests.sh
```

## Recent Improvements

### ✅ Bug Fixed: FCFS Reservation Calculation Missing Cascaded Starts

**Problem:** When multiple jobs cascade-start within a single scheduling
call (e.g., job A completes, freeing enough capacity for job B to start
immediately, which itself frees enough for job C), the reservation time
computed for the next blocked head did not account for jobs decided
earlier in that same call - because `Simulation`'s own `running_jobs` map
isn't updated until after the scheduling call returns the full list of
jobs to start.

**Impact:** Caused an incorrect (too-late) computed reservation, which let
a backfill candidate illegally occupy capacity the real blocked head
needed sooner - visible in `21_sustained_high_load` and similar dense,
high-contention scenarios (`large_200jobs` in `scale/`), where the
divergence compounds across many jobs. Traced empirically: the resource
trace diverges from correct several timestamps before the effect becomes
visible in the job schedule.

**Fix:** Build a local snapshot of `running_jobs` that includes jobs
decided in the current call's cascading-start loop (with their start time
set to the current scheduling instant) before computing the reservation -
see `src/sim/scheduler_fcfs.cpp`. Confirmed this doesn't affect SJF, LJF,
or FCFS_ALT, since none of those three ever return more than one job per
scheduling call.

**Verification:** All 34 comprehensive tests pass; the previously-diverging
resource trace for `21_sustained_high_load` is now identical to the
correct trace at every timestamp, not just approximately close.

### ✅ Bug Fixed: Fixture Data Integrity Issues (multiple, found together)

Several independent issues surfaced while re-examining test fixtures:
- 5 comprehensive tests (07, 08, 28, 29, 31) had multiple jobs sharing a
  submit time with fully identical parameters, meaning an identity-mixup
  bug wouldn't have been visible in the output. Fixed by giving each tied
  job a distinguishing node count or duration.
- 2 unit tests (`simple_2jobs.csv`, `timestamp_epoch_simple.csv`) used
  queue name `"batch"` instead of the required `"pbatch"`, silently
  loading zero jobs.
- 2 scale tests (`medium_50jobs`, `large_200jobs`) had broken expected
  output files - some jobs left as `0,0` placeholder (never actually
  scheduled), and resource traces that were byte-identical across
  differently-sized tests. Root cause: `scale/` never had a generator
  script covering it (see `docs/TESTING_GUIDE.md`). Fixed by adding
  `scripts/generators/generate_scale_expected_outputs.py` and
  regenerating.
- 3 scale tests (`xlarge_500jobs`, `xlarge_500jobs_v2`, `huge_2000jobs`)
  have corrupted *input* data (identically truncated regardless of
  filename) and remain unfixed - this needs new source data, not a
  regeneration.

### ✅ Bug Fixed: Resource State Recording

**Problem:** When multiple jobs were started in a batch (e.g., multiple backfills), the simulator recorded resource state only once after all jobs started, missing intermediate states.

**Impact:** 
- Tests 21 (50 jobs) and 23 (30 jobs) were failing
- Resource traces showed divergence from expected
- Job schedules were affected due to wrong resource accounting

**Root Cause:** In `src/sim/sim.cpp`, resource recording was outside the job start loop:
```cpp
// BEFORE (buggy)
for (job : jobs_to_run) {
    start_job(job);  // Start multiple jobs
}
record_resource_state();  // Record only once
```

**Fix:** Moved recording inside the loop (lines 328-340 and 442-465):
```cpp
// AFTER (correct)
for (job : jobs_to_run) {
    start_job(job);
    record_resource_state();  // Record after EACH job
}
```

**Verification:**
- All 34 comprehensive tests now pass
- Added 7 new tests (28-34) specifically targeting this bug
- Tier 5 tests (16-19) verify multiple simultaneous backfills work correctly

### ✅ Python Reference Backfill Window Fix

**Problem:** Python reference used `>` instead of `>=` for backfill window check, allowing jobs to backfill when `completion_time == reservation_time`.

**Why Wrong:** Resources don't become available instantly when a job completes. The FCFS head must wait for the completion event to be processed.

**Fix:** Changed to `completion_time >= reservation_time` (reject), meaning only `< reservation_time` is accepted.

**Comment Added:** Clear documentation in both C++ (`scheduler_fcfs.cpp` line 99) and Python explaining why strict `<` is required.

## Key Testing Principles

### Dual Validation (Comprehensive Tests)

Every comprehensive test verifies **TWO things**:
1. **Job schedules match** - Start and end times for all jobs
2. **Resource traces match** - Resource states at every event

A test only passes if **BOTH** match. This dual validation:
- Caught the resource recording bug (schedules matched early, traces diverged)
- Prevents silent failures in resource accounting
- Ensures consistency between schedule and resource accounting - not
  independent proof of correctness (see below)

### Expected Output Generation

Comprehensive and scale test expected outputs are generated by the
**Python reference implementation** (`scripts/python_reference_scheduler.py`),
not hand-calculated. This means passing tests demonstrate agreement with
that reference, not independently verified correctness - see
`docs/TESTING_GUIDE.md` for what this distinction means and why it
matters.

**Advantages:**
- Fast to generate for complex scenarios (50+ jobs)
- Python code is simple and easy to verify by inspection
- Can test large-scale scenarios

**Limitations:**
- Not true analytical testing (two implementations, not independent mathematical verification)
- If Python has a bug, C++ would match wrong behavior
- Both could share the same algorithmic misunderstanding

For critical correctness, manual verification of simple tests (2-5 jobs) is still recommended.

### Test Organization

Tests are ordered by complexity (see `docs/testing/TEST_SUITE_ORDERED_BY_COMPLEXITY.md`):
1. Start with simplest (2 jobs, pure FCFS)
2. Build up complexity (backfilling, simultaneous events)
3. Stress test with scale (50 jobs)

If a basic test fails → fundamental issue
If only complex tests fail → edge case or scaling issue

(See "4. Scale Tests" above for `test_traces/scale/` details.)

## Test Infrastructure

### Test Runners

Runners that actually exist in `tests/`:

```bash
run_unit_tests.sh          # unit/ tests
run_feature_tests.sh       # feature/ tests
run_replay_tests.sh        # replay methodology (hardcodes 3 comprehensive/ tests)
run_configs_tests.sh       # protobuf config tests (requires -DDR_EVT_ENABLE_PROTOBUF=ON)
run_python_tests.sh        # python API tests (requires -DDR_EVT_BUILD_PYTHON=ON; not verified in this pass)
run_streaming_tests.sh     # C++ streaming API test binary (requires building test_streaming_api target; not verified in this pass)
run_grpc_tests.sh          # gRPC client/server tests (requires -DDR_EVT_ENABLE_GRPC=ON)
test_all_dr_evt.sh         # comprehensive/ tests (see below)
test_fcfs_comprehensive.sh # queue implementation differential testing (see below)
benchmark_block_sizes.sh   # queue implementation performance comparison (see below)
```

`test_all_dr_evt.sh` runs the simulator against every `comprehensive/`
test and diffs against `expected_output.csv`/`expected_resources.csv`.
Verified in this session: 33/34 pass. The one exception,
`28_simultaneous_completions_backfill`, is a false failure - the script's
resource-trace comparison is overly strict about the internal *order* in
which simultaneous end/start events get recorded within the same
timestamp, not an actual scheduling or accounting discrepancy. Both the
schedule and the final settled resource state at every timestamp match
exactly (confirmed by direct inspection: same 60-used/40-free final state
at t=100, just reached via a different intermediate event order than the
Python reference produces). An earlier version of this document claimed
this script didn't exist without actually checking - it does, and it
mostly works.

There is no equivalent runner for `scale/` - that has been done manually
during development. `compare_with_analytical.sh`, referenced elsewhere in
older docs, does not exist in this checkout.

`test_fcfs_comprehensive.sh --correctness` checks something different from
`test_all_dr_evt.sh`: not whether the C++ simulator matches the Python
reference, but whether all four FCFS wait-queue implementations
(`--queue_impl deque/multimap/block/circular`) produce byte-for-byte
identical output to each other, across the same 34 comprehensive traces.
Runs in CI. See `docs/dev/design-decisions/BLOCK_QUEUE.md` and `docs/dev/design-decisions/CIRCULAR_QUEUE.md` for what
each non-default implementation is, and `docs/TESTING_GUIDE.md` for how
this differs from the Python-reference comparison above.

`benchmark_block_sizes.sh` measures performance (not correctness) across
every block size and the circular queue, against a 10,000-job trace by
default.

## Troubleshooting

### Build Not Found

```bash
cd build
cmake ..
make -j4
cd ..
```

### Test Fails

1. Check output:
   ```bash
   ./build/simulator <input> --total_nodes 100 \
       --trace_format simple --timestamp_format epoch \
       --duration_mode exact --outfile /tmp/test.csv
   cat /tmp/test.csv
   ```

2. Compare with expected output:
   ```bash
   diff /tmp/test.csv tests/test_traces/comprehensive/<name>.expected_output.csv
   ```

3. Check for:
   - Resource over-subscription
   - Incorrect event ordering
   - Jobs not completing

### All Tests Fail

- Rebuild: `cd build && make clean && make -j4`
- Check simulator runs: `./build/simulator --help`

## Contributing

When adding new features:

1. Write tests first (test-driven development)
2. Add to appropriate test category
3. Regenerate expected outputs via the relevant generator script if the
   scheduler's behavior changed intentionally (`generate_all_expected_outputs.py`,
   `generate_scale_expected_outputs.py`)
4. Run `run_unit_tests.sh`, `run_feature_tests.sh`, `run_replay_tests.sh`,
   plus manual comparison against `comprehensive/`/`scale/`'s expected
   files (see "Running Tests" above - no single script covers those yet)
5. Update this README if adding a new test category
