# Test Traces for DR_EVT Scheduler

This directory contains test traces for the DR_EVT job scheduler simulator.

## Directory Structure

```
test_traces/
├── comprehensive/        # Scheduler correctness tests (34 tests)
│   ├── *.csv                    # Input traces (simulation mode)
│   ├── *.expected_output.csv    # Expected job schedule
│   ├── *.expected_resources.csv # Expected resource timeline
│   ├── *.construction.md        # Scenario description per test
│   └── *.answer.json            # Constraints (not currently validated
│                                 # by any script - see note below)
├── unit/                 # Basic I/O and format tests (7 tests)
├── feature/              # Policy and mode comparison tests (3 tests)
└── scale/                # Larger-scale tests (7 tests, 3 currently broken)
```

## History note

This directory previously described (and this README previously documented)
a `correctness/` scheme: 19 hand-traced analytical tests plus 4
cross-validation tests at 50-2000 jobs, generated by
`scripts/generate_correctness_traces.py` / `generate_all_analytical_oracles.py`
and checked by `scripts/verify_against_analytical.py`. That directory does
not exist in this checkout - the test suite moved to the `comprehensive/`
design below at some point without those scripts, the old `correctness/`
directory, or this file being cleaned up. `scale/`'s file naming
(`small_10jobs`, `medium_50jobs`, `large_100jobs`/`large_200jobs`,
`xlarge_500jobs`, `huge_2000jobs`) matches the abandoned scheme's "50-2000
job cross-validation" tests almost exactly, and appears to be an orphaned
remnant of it - see the `scale/` section below.

## Test Categories

### Comprehensive Tests (34 tests)
**Location:** `comprehensive/`
**Purpose:** Verify EASY backfilling scheduler correctness
**Node count:** 100

**How expected outputs are generated:** by running
`scripts/python_reference_scheduler.py` (via
`scripts/generators/generate_all_expected_outputs.py`), **not** hand-calculated.
There is no independent ground truth here - the C++ implementation and the
Python reference were both written by the same process, so agreement
between them demonstrates consistency, not independent verification of
correctness. See `docs/TESTING_GUIDE.md` for more on this distinction.

- Tiers 1-9, covering FCFS, basic and competitive backfilling, simultaneous
  events, large-scale (20-50 job) scenarios, and early completion. See
  `comprehensive/TEST_ORDER.md` if present, or `construction.md` per test.

### Unit Tests (7 tests)
**Location:** `unit/`
**Purpose:** Basic I/O, formats, simple scenarios

- Timestamp formats (epoch, ISO)
- Simple job traces (2-3 jobs)
- Sequential execution
- Timezone handling

**Known issue:** `sequential_3jobs.csv` and `simple_basic.csv` are still
broken as of this writing - their input data is genuinely incomplete
(`begin_time == end_time` placeholder values for 2 of 3 jobs, and a wrong
submit time on the one job that does load), not just a formatting issue.
A working, correctly-formatted equivalent already exists as
`sequential_3jobs.trace` (6-column, tab-separated replay format) - consider
using that instead of fixing the `.csv` versions from scratch.

**Queue name requirement:** the `queue` field in any trace must be
`pbatch` (or `pbatch0`-`pbatch3`) - other values, including the seemingly
reasonable `"batch"`, are silently dropped during load (see
`src/trace/job_io.cpp`'s queue filter). This fails silently, not loudly: a
trace with the wrong queue name loads zero jobs and produces an empty
`expected_output.csv`, with no error printed. This is exactly how
`simple_2jobs.csv` and `timestamp_epoch_simple.csv` broke previously.

### Feature Tests (3 tests)
**Location:** `feature/`
**Purpose:** Policy and mode comparisons

- Conservative vs EASY backfilling
- Sustained replay vs sustained simulation

**Known limitation:** conservative backfilling is not actually implemented
as a distinct algorithm - `BackfillPolicy::CONSERVATIVE` currently runs the
same logic as EASY (see `src/sim/scheduler_fcfs.cpp`). `conservative_backfill.csv`
passes, but its scenario doesn't put any job in a position where conservative
and EASY would actually produce different schedules, so it doesn't catch
this gap.

### Scale Tests (7 tests, 4 working)
**Location:** `scale/`
**Purpose:** Larger job counts than `comprehensive/`'s 20-50 job ceiling
**Node count:** 795 (matches `src/dr_evt_types.hpp`'s default - NOT
`comprehensive/`'s 100. Several jobs in these traces request up to 497
nodes and cannot be scheduled at all under 100 nodes.)

**How expected outputs are generated:** `scripts/generators/generate_scale_expected_outputs.py`,
added to close the gap described in the History note above - `scale/` had
no generator at all before this. Uses the same Python reference
implementation as `comprehensive/`, at 795 nodes.

**Working (4):** `small_10jobs`, `medium_50jobs`, `large_100jobs`, `large_200jobs`.

**Broken, excluded from the generator (3):** `xlarge_500jobs.csv`,
`xlarge_500jobs_v2.csv`, and `huge_2000jobs.csv` are identically corrupted
regardless of filename - all three are truncated to exactly 392 data rows
(not 500, 500, or 2000) with the same malformed final row (`188,,,,`).
This is input-data corruption, not something a generator script can fix -
these three need their source data rebuilt or replaced.

## Additional Test Types

### Replay Tests (3 tests, verified to also pass on more)
**Runner:** `../run_replay_tests.sh`

Verifies replay mode reproduces simulation resource usage:
1. Run simulation mode → job schedule trace + resource trace
2. Feed the schedule trace back in as replay-mode input (auto-detected via
   the `begin_time`/`end_time` columns present in simulator output)
3. Compare: resource traces must match exactly

The runner script hardcodes 3 tests from `comprehensive/`; this methodology
has also been verified to pass against all 34 `comprehensive/` tests plus
4 `scale/` tests (see project history/session notes for details).

### Configuration Tests
**Location:** `../test_configs/*.pb`
**Runner:** `../run_configs_tests.sh`

Verify protobuf config files match CLI options. Requires building with
`-DDR_EVT_ENABLE_PROTOBUF=ON`; not exercised by this document's own
verification pass since that build option wasn't available.

### Streaming / Python API Tests
**Files:** `../test_streaming_api.cpp`, `../test_batch_vs_streaming.cpp`,
`../test_python_api.py`, `../mpi_job_feeder.cpp` (MPI-based)

Test the streaming/online submission API. These are hardcoded C++/Python
test programs, not CSV fixtures.

## Test Status

As of this writing (after fixing a scheduler reservation-calculation bug
affecting multi-job cascading backfills, and after the fixes described
above): `comprehensive/` 34/34, `feature/` 3/3, `scale/` 4/4 (working
subset), replay methodology verified across all of the above. `unit/` has
2 known-broken tests (see above). Three `scale/` input files remain
corrupted and unfixed.

This "Test Status" section reflects a point-in-time verification, not an
automated, continuously-re-run check - there is no CI or validator script
in this repo that currently re-confirms these numbers on each change (see
`docs/TESTING_GUIDE.md`'s discussion of the `.answer.json` constraint
files, which are also not currently validated by anything). Treat this
section as informative, not authoritative, and re-verify before relying
on it.
